# Generate Daily Report Skill

此技能協助 Agent 根據 Git 的變更紀錄，自動撰寫符合使用者風格的工作日誌或報表。

## 🎯 執行目標

1. **精準提取**：正確執行腳本提取指定區間的 Git 變更。
2. **合理分配**：過濾瑣碎變更，將有意義的工作項目合理分配至指定的工作天數中。
3. **風格一致**：嚴格模仿使用者提供的範本風格與用語習慣（預設使用台灣繁體與民國年格式）。
4. **安全產出**：在寫入實體檔案前，必須先與使用者確認內容。

## 🛡️ 防護網與邊界條件 (Guardrails)

1. **腳本錯誤攔截**：若執行 `get_change_summary.ps1` 時發生錯誤（如 Commit Hash 無效或找不到分支），**必須立刻停止執行並向使用者回報錯誤**，不可強行瞎掰內容。
2. **繁體中文強制**：全篇報表必須使用台灣繁體用語（如：實作、優化、除錯、專案、介面等），絕對不可出現簡體字或中國大陸慣用語。
3. **確認後寫入**：**絕對不可在未經使用者同意前直接建立檔案**。必須先輸出草稿，使用者回覆 OK 後，再使用 `write_to_file`。

## 📥 參數

- `Commit1` (Required): 起始 Commit Hash。
- `Commit2` (Required): 結束 Commit Hash。
- `Days` (Optional): 報表需涵蓋的天數 (例如 3 天)。**若未提供或使用者要求推薦，Agent 將自動根據程式碼異動量進行評估並提出推薦天數。**
- `StartDate` (Optional): 報表的起始日期 (例如 2026/02/13)，若未提供則預設從當前日期或 Commit 最新日期開始往後面日期推算。
- `StyleFile` (Optional): 風格範本檔案路徑，預設為 `STYLE_TEMPLATE.txt`。
- `NotesFile` (Optional): 特殊行程註記檔案路徑，預設為 `SPECIAL_NOTES.txt`。

## 📊 異動量評估與天數推薦機制 (Change Volume Assessment & Recommendation)

若使用者未指定天數（`Days`）或主動要求推薦，Agent 應依據以下量化指標評估並向使用者提出推薦天數及理由：

1. **指標定義**：
   - **C** (Commits 數量)
   - **F** (改動檔案數量)
   - **L** (總異動行數，即 Insertions + Deletions)

2. **推薦級距表**：
   - **🟢 建議 1 天**：
     - 指標範圍：C <= 3 且 F <= 3 且 L <= 100 行。
     - 適用場景：主要是單一功能的小修補、簡單 Bug 修復、或是零星的樣式/註解調整。
   - **🟡 建議 2 ~ 3 天**：
     - 指標範圍：C 在 4 ~ 10 之間，或 F 在 4 ~ 10 之間，或 L 在 100 ~ 500 行之間。
     - 適用場景：包含一個完整功能的開發、多個 Bug 修復，或是中等規模的重構（例如提取共用模組）。
   - **🔴 建議 4 ~ 5 天 (約一週工作量)**：
     - 指標範圍：C > 10，或 F > 10，或 L 在 500 ~ 1500 行之間。
     - 適用場景：涉及多個模組的重構、多個新功能開發，或是重大的架構拆分（如巨型模組拆分）。
   - **🟠 建議 6 ~ 8 天 (約一週半工作量)**：
     - 指標範圍：L 在 1500 ~ 3000 行之間。
     - 適用場景：包含多個大模組的重構優化、大型功能演進，或是跨多個模組的體驗改造。
   - **🟣 建議 9 ~ 12 天 (約二至三週工作量)**：
     - 指標範圍：L > 3000 行。
     - 適用場景：極大規模的重構、大型功能連續開發、涉及全系統級別的架構拆分與多模組清理，建議以兩週左右的天數合理稀釋，避免每日工作飽和度顯得過高。

3. **推薦流程**：
   - 在執行步驟 2 獲取變更摘要後，Agent 需先計算出 **C**, **F**, **L** 指標（可透過 `git diff --stat <Commit1> <Commit2>` 獲取總異動行數）。
   - 在草擬報表前，先向使用者報告指標數據，並回覆：「*根據本次異動分析（Commits: C 個, 檔案: F 個, 總行數: L 行），為您推薦生成 X 天的工作報表，原因為：[簡短理由]。請問您是否同意以 X 天進行生成？（亦可指定其他天數）*」
   - 獲得使用者確認後，再繼續執行步驟 3 進行草擬。

## ✅ 執行步驟 (Checklist)

### 步驟 1：讀取指引檔案
請先使用 `view_file` 讀取以下檔案：
1. **風格範本** (預設 `STYLE_TEMPLATE.txt`)：了解撰寫格式。
2. **特殊行程註記** (預設 `SPECIAL_NOTES.txt`)：檢查是否有特定日期的特殊事件或休假。

### 步驟 2：執行提取腳本
請執行以下 PowerShell 指令來獲取變更摘要：
```powershell
./.agent/skills/generate_daily_report/scripts/get_change_summary.ps1 -Commit1 <Commit1> -Commit2 <Commit2>
```
*(注意：若腳本拋出錯誤，請立即中斷任務並報告。)*

### 步驟 3：閱讀輸出並生成草稿 (Drafting)
讀取腳本輸出的 `=== GIT CHANGE SUMMARY ===` 內容，並結合**指引檔案**進行撰寫。

**思考過程：**
1. 分析 Commit Log 中的 `Subject`, `Body` 與 `Files Changed`。
2. **識別主要完成的工作項目** (Feature, Fix, Refactor 等)：
    - **過濾瑣碎任務**：排除僅需極短時間完成或無實質功能影響的變更。
    - **合併小項**：若多個 Commit 屬於同一個功能或修正，請將其彙整為單一的工作點。
3. **處理日期與特殊行程**：
    - 若有提供 `StartDate`，則從該日期開始，依照 `Days` 數量依序遞減。
    - **預設日期格式**：除非使用者另有指定，否則預設轉換為**民國年格式**（例如：`115.06.01` 或 `115年6月1日`）。
    - **排除日期**：排除週末 (週六、週日) 與台灣國定假日 (如需確認可使用 `search_web`)。
    - **對齊特殊行程**：優先填入 `SPECIAL_NOTES.txt` 中與日期對應的內容。
4. 將工作項目**均勻且合理地分配**到計算出的工作日中：
    - 若 Git 提取的 Commit 數量較少但指定天數較長，請**更細緻地拆解 Git 變更內容**（例如：將單一功能的開發細分為「UI 切版與樣式調整」、「核心邏輯實作」或「邊界條件與錯誤處理」等步驟）來填補分配所有天數。
5. **產出草稿**：在對話框中印出完整的報表草稿（純文字格式，不要使用 Markdown 語法如 `#`、`*` 等），並詢問使用者：「這是為您生成的報表草稿，請問是否有需要調整的地方？若無問題我將為您建立檔案。」

### 步驟 4：確認後寫入 (Save to File)
在獲得使用者明確的確認或修改指示後：
- 將最終報表內容儲存為純文字檔 (.txt)，**絕對不可包含任何 Markdown 格式標籤**。
- 檔名建議：`Daily_Report_<Commit2>.txt` 或使用者指定的名稱。
- 使用 `write_to_file` 工具建立檔案。
